# 后续路线与技术取舍

原六周方案的主要工程链路已在 `v2` 落地，当前实现见 [架构流程](ARCHITECTURE.md)，历史交付见 [变更记录](CHANGELOG.md)。本页只保留未完成验收与后续触发条件，避免把已完成工作继续列为计划。

## 1. 优先补齐的验收

| 优先项 | 下一步 | 完成依据 |
| --- | --- | --- |
| 独立人工参考与 Judge 校准 | 人工核对来源、年度与答案；另建未参与调参的独立问题，抽检至少 30 个任务 | 审阅人、参考原文、快照哈希与评分记录齐全；格式通过不代替事实核验 |
| 中文 Embedding 上线决策 | 在独立集比较当前混合检索与 BGE 候选，并统计召回、回答、延迟和资源 | 收益足够稳定再新建集合重建、切换、保留旧索引回退；不混用 384/512 维向量 |
| 协作与工具循环开关 | 比较 single/composed、循环开关对任务成功率、调用量与失败率的影响 | 真实收益超过波动与成本，再调整默认值；当前仍 single、tool_loop=false |
| 部署与可观测性 | 修复可用镜像源后的标准干净构建，连接真实 Langfuse，执行页面视觉审查 | 各项真实结果分别记录；本地镜像复用与模拟 HTTP 测试不代替验收 |
| 长期运行治理 | 设计匿名身份恢复、存储保留期限、清理/归档和备份恢复 | 明确数据权限与保留规则，验证清理不破坏幂等/恢复语义 |

测评仍沿用“数字/权限硬断言优先，其次评估成功率、拒答与误拒答、引用支持率、p50/p95、每成功任务成本”的顺序。原方案 Recall@8 ≥ 90%、Judge 有效覆盖 ≥ 98% 等属于参考目标，不能用开发集或几例冒烟宣称整体达标。用例结构、冻结方法与当前数字只在 [评测说明](EVALUATION.md) 维护。

## 3. 暂不扩展的技术

| 技术方向 | 重新考虑的触发条件 |
| --- | --- |
| Deep Agents / 通用规划子 Agent | 出现长篇政策研究、文件产物和长任务委派需求，在线短咨询不足以覆盖 |
| Mem0 / Hindsight 等记忆框架 | 当前透明事实契约的维护成本确实过高，且已有可比较的独立记忆基准 |
| GraphRAG / 完整知识图谱 | 时间过滤与证据覆盖仍无法处理经过实测确认的关系推理瓶颈 |
| A2A、AG-UI / A2UI | Agent 独立部署或多个客户端确需共享复杂交互协议 |
| Browser / Computer Use | 离线资料采集遇到普通 HTTP/解析无法处理的动态页面 |
| Agent RL、自优化、多模态 | 有真实业务需求、独立数据、可验证奖励/验收和足够资源 |

可继续研究“时间与证据覆盖感知的自适应检索”：相同资料和独立题集下，对比固定一次检索、固定多轮与按缺项补查，衡量质量和调用成本。这是待验证研究方向，不直接宣称算法创新或领先效果。
